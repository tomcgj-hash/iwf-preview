WAYFINDING SOFTWARE

Indoor wayfinding software: modules, deployment models and integration

Indoor wayfinding software is the platform that stores a venue map, plans routes, serves directory kiosks and phones, and exposes the whole content set through a REST API and SDK. It can run as SaaS, in a private cloud or on-premise, and it connects to the systems a venue already operates.

01

Modules

What the platform contains

One platform carries eight modules: indoor mapping, indoor navigation, AR wayfinding, digital directory, parking guidance, people counting, indoor geofencing, and staff positioning with patrol. They share one content store and one coordinate frame, so a tenant renamed in the editor is renamed in the kiosk directory, the phone search and the AR route in the same publish. Modules are enabled per venue, which lets a group run parking guidance in the buildings that have a car park and leave it out of the ones that do not.

The admin side is a browser application: map editing, POI and tenant content, languages, kiosk management, user roles, integration credentials and reporting. The venue-facing side is a kiosk application, a phone web experience, and an SDK for venues that want wayfinding inside their own app or mini program. Both sides read the same data, which removes the usual drift between a directory screen and a navigation app.

A kiosk server manages the terminal fleet, pushes content, reports per-terminal usage and health, and can run up to 100 directory terminals from one server. Terminals are grouped, so a mall can publish a different promotion loop to each entrance without touching the map. A terminal that loses its network keeps serving cached content, and the console marks it offline until it reconnects.

02

Which deployment model fits your venue?

Three models are supported and the choice is usually decided by data rules rather than by features, because the application is the same in all three. SaaS is fastest to start and we operate it. Private cloud puts the instance in your cloud account, which suits groups with an existing cloud landing zone and internal data policy. On-premise runs inside the building or the data center and is chosen when position data may not leave the network.

The honest trade-off: SaaS costs least to run and updates arrive without a maintenance window you have to plan. Private cloud gives control and a familiar backup regime at the cost of a server owner on your side. On-premise gives the strictest data boundary and the highest operational load, because patching, backups and capacity are yours. We do not pretend these are equivalent.

Updates apply to all three models. When a venue runs on-premise, we ship release packages with notes and a rollback path, and the venue IT team schedules the window. When a venue runs on SaaS or in a private cloud, the update lands on our schedule with advance notice. We agree the notification period in the agreement, so nobody discovers a release from a changed screen on a kiosk.

03

How do the REST API, SDK and webhooks work?

The API is REST over HTTPS with JSON payloads. It exposes venue and floor lists, POIs, search, route requests, kiosk content and usage reports, so a venue app can drive navigation without embedding the map inside its own code. Credentials are issued per venue and per client, with scopes that limit a client to the venues it should see. Requests are rate limited per client, and the limit is stated in the agreement rather than discovered on launch day.

The SDK wraps the same calls for iOS, Android, web and mini program targets, and handles the parts that are tedious to rebuild: map rendering, route display, AR overlay on the camera, location permission handling and offline caching of the active floor. The SDK does not hide the API; anything the SDK does can be done directly if you prefer.

Webhooks push events rather than waiting for a poll. Route started, route completed, geofence entry and exit, patrol check-in and kiosk offline are the common ones. Each delivery is signed and retried with backoff, so a receiving service can be restarted without losing events, and a failed endpoint is visible in the admin console rather than silently dropping data. Every event carries a venue identifier and an object identifier, so the receiving system does not have to look up what changed before it acts.

04

Which systems do you connect first?

Start with the systems that already hold data the visitor asks about. In a mall that is the tenant list and the parking system, because a visitor wants a store and a car, not a route for its own sake. In a hospital it is the appointment or directory data, read-only, so the map never becomes a second source of truth for a department name.

Most integrations are one of three shapes: a scheduled import of a list, a real-time query against an interface, or an event we push outward. Naming the shape early keeps the integration small. A POS link that needs a live transaction feed is a different project from one that needs a daily tenant roster, and we scope them differently. One rule holds across all of them: the map never becomes the master record for data another system already owns.

05

Can one platform run several venues and languages?

Yes. A group account holds multiple venues with separate content, separate maps and separate kiosk fleets, while a group-level administrator can see usage across all of them. Venue editors only see their own venue, which matters when a group runs twenty buildings and does not want each site editing the others. Consolidated reporting compares search success and route completion across venues, so a site that is losing visitors can be found without reading twenty dashboards.

Languages are handled per venue, not per account, because the visitor mix differs by site. Interface strings and POI names are held per language, with right-to-left layout for Arabic. A bilingual hospital in one city and a four-language mall in another can share an account without sharing content, and adding a language does not duplicate the geometry. Translations are managed as content, so a venue can publish a language before the printed signage catches up, or hold one back until the directories match.

06

How are admin roles and the audit trail set up?

Roles are scoped by venue and by function. A venue administrator manages users, content and kiosks for one site. An editor changes POIs and multilingual names but not the walk graph. An operator watches live position, dispatch and alerts. A viewer sees reports only. A staff supervisor handles patrol routes and check-in records. Each role maps to a scope, not to a job title, so a group can combine them as it needs.

Every change is logged with the user, the venue, the object, the before and after values, and the timestamp. The log covers content edits, publishing, user and role changes, integration credential changes and API calls that carry content modification. It exports to CSV for an internal audit, and it is read-only in the interface, because an audit trail an administrator can edit is not an audit trail.

07

What does support look like after go-live?

Supplied hardware carries a 12 month warranty as the standard term, and software updates are included during the support term. Extended support is optional and priced with the scope. Support hours follow business hours Monday to Saturday, 09:00 to 18:00 GMT+8, with a 24 hour response target for a scope issue. A kiosk that is dark at an entrance is handled as an availability issue rather than a content question, because a blank screen at the main door is what visitors judge the venue by.

Availability targets are written into the service agreement per deployment model, because a SaaS instance and an on-premise instance have different failure domains and it would be misleading to quote one number for both. On-premise availability depends on your own infrastructure, and we state which parts of the chain are ours and which are not. What we do not do is quote an uptime figure for a chain that includes your network, your power and your server hardware.

Escalation runs from the support desk to the engineer who built the mapping, which is a shorter path than it sounds because the same team produces the map and answers the ticket. That matters most in the first month, when most tickets are content questions rather than defects. It also means a defect report can end with a data fix rather than a line in a backlog.

08

How do you plan the rollout with your IT team?

A reference rollout is 6 to 10 weeks: survey 3 to 5 days, map production 2 to 3 weeks, platform setup and integration 2 to 4 weeks overlapping with production, then calibration and training about 1 week. The integration track is usually the one that slips, so we start it in week one with the interface list rather than waiting for the map.

What we need from IT before setup: a decision on deployment model, network access for kiosks and devices, firewall rules for the platform endpoints, certificates or domain names if the venue is hosting the front end, and a named owner for each integration. What we need from operations: the tenant list, opening hours, entrances, closed areas and the staff who will be trained.

Training is split by role, because an editor and a kiosk administrator need different sessions. The editor session is half a day and covers content changes end to end. The administrator session covers users, kiosk groups, publishing and reports. Both end with the venue making a real change under supervision, which is the only way to know the training worked.

FAQ

Common questions

Can't see your question? Send it with your floor count and we answer within one working day.

Ask a specific question

Is the software licensed per venue or per user?

Per venue, with administrator seats included in the scope. A group account covers several venues under one agreement, and each venue can carry its own editors and kiosk groups. We quote against venue count, modules enabled, kiosk terminals and integration scope rather than against headcount, which keeps the cost predictable as staff change.

Can we run the platform on-premise inside our network?

Yes. On-premise deployment runs on a server or virtual machine you provide, with a database and network access from the devices and kiosks. You take on patching, backup and capacity, and we ship release packages with notes and a rollback path. Sites with strict data rules choose this model even though it costs more to operate.

What can the REST API actually do?

Read venues, floors and POIs, run a search, request a route, fetch kiosk content and pull usage reports. Content changes through the API are supported with write scope, and every such call lands in the audit trail. The SDK wraps the same endpoints for app builders, so nothing is available in the app that the API cannot reach.

How long does integration with our existing systems take?

A scheduled tenant import is days. A parking interface with plate recognition is the medium case, typically one to two weeks of joint work. A fire alarm or access control link needs agreement on the trigger and on who owns the logic, which is usually slower than the code. We list integrations with an effort estimate before the contract, not after.

Does the platform support several buildings in one account?

Yes. A group account holds multiple venues, each with its own map, content, languages and kiosk fleet, and a group administrator sees usage across them. Venue editors are scoped to their own site. Buildings that a visitor can walk between should be linked on one site map so a single search can cross them.

What happens to our content if we end the agreement?

You export it. POIs, layers, the walk graph and translations come out as JSON, and floor rendering comes out as SVG, both documented field by field. Map data produced for your venue belongs to the venue. The export is a standard feature rather than a negotiation, because leaving should be a decision, not a trap.

How is availability handled for kiosks in a live venue?

Kiosks cache their content and the active floor, so a network interruption does not blank a directory screen. The platform reports a terminal as offline in the admin console, and the webhook fires so your operations team hears about it from the system rather than from a visitor. Recovery is automatic on reconnect.

Do you offer a trial before a full deployment?

We do a paid pilot on one floor or one building section, with real content and a real walk test, because a demo map proves nothing about calibration. The pilot output is a working map, a route list and a measured accuracy result, and it carries into the full deployment rather than being thrown away.
